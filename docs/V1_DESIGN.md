# V1 deterministic baseline design

Status: frozen engineering design before inspection of V1 outcomes, 2026-09-29. V0 acceptance and its recorded hashes remain unchanged. V1 is a public-data research layer; an intent is not an order or a fill.

## Input and ordering

The V1 engine receives one immutable V0 `book.View` and a read-only current book quote after each **recorded `ClockTick`**, in recorder ordinal order. Both the live collector and raw replay call the same V0 normalizer/book processor and the same V1 engine. The engine receives no future iterator, outcome, final manifest, system clock, or uncommitted event. The quote accessor copies sorted levels; it does not change V0 state JSON or hashes. Non-tick events update V0 book before a later tick can sample it. Equal times are resolved by ordinal. Every sample is stamped with the tick's `UsableFromTime`, ordinal, book generation, last book ordinal, and last book available time. Source event time never moves a sample backward.

Only `HEALTHY` books with a noncrossed BBO, current generation, and last book age in `[0,2s]` are eligible. A heartbeat does not refresh book age. A missing or ineligible tick resets rolling warm-up; a gap over two seconds between consecutive samples resets it too. A new epoch/generation always resets it. The live operational watchdog remains an additional publication veto; an offline replay cannot infer a missed live deadline. V1 derived files have independent schema/config hashes and do not modify accepted V0 outputs.

## Frozen V1 feature and signal card

One sample is taken per eligible recorded one-second tick; an equal-time tick does not add a duplicate sample. All windows contain the current sample and the specified number of immediately preceding *eligible, contiguous* tick samples in the same generation. No event-time bar or later revision is used. One intent is emitted at the first recorded tick in each UTC minute, including warm-up and unhealthy minutes; feature values appear only after warm-up. No output is backdated. The exact decision horizon is **300 seconds from hypothetical entry**. This Internet capture architecture makes second-scale execution claims inappropriate.

| Value | Formula / units | Warm-up and mechanism |
| --- | --- | --- |
| Midpoint, spread | `(best_bid+best_ask)/2` USD/BTC and `(ask-bid)/mid * 10,000` bps | Current healthy quote; spread is immediate friction. |
| `return_60_bps` | `10,000 * ln(mid_now/mid_60_samples_ago)` | 61 contiguous samples; recent repricing may persist. |
| `mean_300` and `displacement_300_bps` | Arithmetic mean of 300 current and prior midpoint samples; `10,000 * ln(mid_now/mean_300)` | 300 samples; local displacement may revert. |
| `rms_900_bps_sqrt_s` | Root mean square of the last 900 one-second midpoint log returns in bps | 901 samples; uncertainty/volatility context, not an independent directional signal. |

Numeric feature outputs are rounded to integer **micro-bps** (0.000001 bp) before serialization or threshold comparison. Inputs are validated canonical decimal strings, converted to IEEE-754 binary64 at the V1 boundary; all rolling updates use fixed event order and a fixed Go toolchain. Repeated identical replay must produce byte-identical V1 outputs. Nonfinite or nonpositive values are unavailable and force `NO_TRADE`.

The descriptive regime is `WIDE` if spread exceeds 10 bps, otherwise `VOLATILE` if RMS exceeds 1 bp per square-root second, otherwise `NORMAL`; before warm-up it is `UNKNOWN`. These fixed, unfit thresholds are context labels, not measured market regimes or tuned gates. The momentum baseline is `LONG` for return above +10 bps, `SHORT` below -10 bps, else flat. The independent mean-reversion comparator is `SHORT` for displacement above +10 bps, `LONG` below -10 bps, else flat. Boundary equality is flat. Both are uncalibrated hypotheses, not separate probabilistic evidence; the initial decision policy uses only momentum, while the reversion result is recorded for paired research comparison.

## Opportunity and intent

The configured research reference is **USD 100 at the decision midpoint**, yielding a fixed BTC quantity for that hypothetical evaluation episode. This is a cost probe, not account sizing. The scenario assumes taker fees of **20 bps per side** and an additional **5 bps per side** adverse execution allowance. These are deliberately fixed research assumptions, not a claim about the current Kraken fee schedule or a possible real fill. Sweep the displayed 100-level book for that quantity; if either side has insufficient depth, costs are unavailable. Entry buys consume asks and sells consume bids; exit reverses sides. The same-side current-book round trip embeds spread and depth in the execution prices. Fees and the extra allowance are applied once per side; spread is never charged again. This scenario excludes tax and exchange/account constraints.

The predeclared opportunity screen accepts a momentum direction only when its absolute 60-second return proxy exceeds the current-book round-trip friction plus a fixed 10-bp uncertainty margin. The proxy is **not** an estimated expected return and no probability or profit forecast is emitted. `SHORT` additionally requires an explicit, versioned hypothetical short mechanism with borrow/carry assumptions; V1's default spot-only configuration has none, so a bearish candidate becomes `NO_TRADE/SHORT_FEASIBILITY_UNKNOWN`. This remains true even if the short comparator appears favorable. No account, leverage, quantity, order type, or execution endpoint is encoded in an intent.

`TradeIntent` schema v1 has deterministic ID (`run_id:decision_ordinal:v1`), run/instrument, as-of ordinal/time, action, horizon, expiry, quote generation/book ordinal/book age, current BBO and reference notional, fee/allowance and estimated round-trip friction in bps, versioned feature/regime/signal results, health, reason codes, and configuration digest. It omits unsupported probabilities, expected net return and measured live publication time. A separate live journal may add measured decision-ready/publication times; replay does not overwrite those operational facts. `NO_TRADE` is emitted for unhealthy/stale/warm-up/invalid depth/flat signal/insufficient margin/unknown short feasibility with stable reason codes.

## Historical evaluator and controls

The evaluator is a **separate consumer** of immutable intents and subsequent quotes. It cannot call back into the decision engine. It never treats a midpoint as an executable quote. A research-only delay of two seconds after the decision as-of time models publication plus entry latency; the first healthy quote at or after that boundary, within two seconds, is entry. Exit is the first healthy quote at or after entry plus 300 seconds, within two seconds. An unhealthy or over-age book anywhere between entry and exit censors the episode; an absent endpoint also censors it. The fixed reference BTC quantity is set at the decision midpoint. Long uses ask VWAP to enter and bid VWAP to exit; hypothetical short reverses sides and includes an extra conservative 10-bp daily borrow/carry assumption in research comparisons only. Fees apply to each side's executed notional, and the 5-bp allowance applies adversely to each side. Report midpoint gross direction skill separately from executable-side net return. Missing depth censors rather than assumes a fill. This is a hypothetical immediate-taker quote calculation, not a realized trade.

The same health/quote-age eligibility mask and decision timestamps apply to action policy, simple momentum, simple mean reversion, always-long, deterministic random direction at matched nonflat momentum frequency, and `NO_TRADE`. All comparators are evaluated on paired episodes with the same available endpoints; action frequency and calendar coverage are reported separately. Overlapping five-minute labels are dependent; reports disclose episode count and do not treat one-minute samples as independent trials. The accepted roughly one-day V0 tape is **development/exploratory engineering data**, not a sealed final test or evidence of durable profitability. No threshold is selected from it. A future untouched chronological period is needed for economic claims. Every changed threshold/horizon/cost must be recorded in an experiment ledger before evaluation; exposed periods become development data.

## Acceptance gate

V1 engineering acceptance requires: pure incremental engine and separate evaluator; boundary/warm-up/gap/staleness/future-poison and side/depth/cost tests; identical V1 output hashes from repeated full V0 raw replay (and live/common-prefix comparison if a V1 live run is made); a complete exploratory report with counts, coverage, censoring, paired controls, regime slices, cost and sensitivity disclosures; `go test -count=1 ./...`, `go test -race -count=1 ./...`, `go vet ./...`, `gofmt -l cmd internal`, `git diff --check`; and an adversarial final audit. A short live smoke is desirable but cannot prove profitability. No positive return is required. If the full gate has not passed, leave V1 incomplete and do not shut down the machine.
